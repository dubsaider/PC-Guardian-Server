# Резюме рефакторинга: Разделение текущего состояния и истории

## Цель рефакторинга

Оптимизировать производительность API и подготовить архитектуру для визуализации истории изменений конфигураций ПК.

## Выполненные изменения

### 1. Модели данных

#### `PCCurrentConfiguration` (новая модель)
- **Назначение**: Хранение текущего состояния конфигурации ПК
- **Особенности**: 
  - Одна запись на ПК (обновляется при каждом изменении)
  - Первичный ключ: `pc_id`
  - Быстрый доступ для списка ПК

#### `PCConfiguration` (обновлена)
- **Назначение**: Хранение полной истории изменений конфигурации
- **Особенности**:
  - Множество записей на ПК (append-only)
  - Используется для истории, графа изменений, аудита

### 2. Репозитории

- **`CurrentConfigRepository`**: Новый репозиторий для работы с текущим состоянием
  - `find_by_pc_id()` - найти текущее состояние для ПК
  - `find_all()` - найти текущее состояние для списка ПК
  - `create_or_update()` - создать или обновить текущее состояние

### 3. Сервисы

#### `ConfigService`
- Добавлен метод `create_current_configuration()` для создания текущего состояния из domain модели

#### `ConfigurationProcessingService`
- Обновлен для сохранения в обе таблицы:
  1. Сохраняет в `PCConfiguration` (история)
  2. Обновляет `PCCurrentConfiguration` (текущее состояние)

### 4. API Endpoints

#### `GET /api/pcs`
- **Оптимизирован**: Использует `PCCurrentConfiguration` вместо загрузки всех конфигураций
- **Производительность**: 1 запрос вместо N+1 запросов
- **Результат**: Значительное ускорение загрузки списка ПК

#### `GET /api/pcs/{pc_id}`
- Обновлен для использования `current_config` вместо `latest_config`
- Возвращает текущее состояние и эталонную конфигурацию

#### `GET /api/pcs/{pc_id}/history` (новый)
- Возвращает полную историю изменений конфигурации ПК
- Поддерживает пагинацию (`skip`, `limit`)
- Сортировка по `timestamp` (от новых к старым)

### 5. Миграция БД

- Создана таблица `pc_current_configurations`
- Заполнена данными из последних конфигураций существующих ПК
- Создан индекс на `updated_at` для ускорения запросов

## Преимущества

### Производительность
- **Список ПК**: Загрузка из одной маленькой таблицы (1 запрос)
- **Детали ПК**: Быстрый доступ к текущему состоянию
- **История**: Загружается только когда нужна

### Масштабируемость
- Текущее состояние: маленькая таблица (1 запись на ПК)
- История: может расти без ограничений
- Разделение ответственности: разные таблицы для разных целей

### Функциональность
- Готовность к визуализации истории изменений
- Возможность построения графа изменений
- Отслеживание изменений по компонентам
- Временной анализ изменений

## Технические детали

### Структура таблиц

```sql
-- Текущее состояние (быстрый доступ)
CREATE TABLE pc_current_configurations (
    pc_id VARCHAR(255) PRIMARY KEY,
    updated_at DATETIME NOT NULL,
    agent_version VARCHAR(50),
    -- компоненты как JSON
    ...
);

-- История изменений (полная история)
CREATE TABLE pc_configurations (
    id INTEGER PRIMARY KEY,
    pc_id VARCHAR(255) NOT NULL,
    is_baseline BOOLEAN,
    timestamp DATETIME NOT NULL,
    agent_version VARCHAR(50),
    -- компоненты как JSON
    ...
);
```

### Поток данных

```
Kafka Message
    ↓
ConfigurationProcessingService
    ↓
├─→ PCConfiguration (история) - сохраняется всегда
└─→ PCCurrentConfiguration (текущее) - обновляется
    ↓
EventService (создает события изменений)
```
